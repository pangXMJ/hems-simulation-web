系統運作架構與流程規格書
一、 核心架構：雙軌分離設計與數位孿生
本系統採用「離線規劃（Offline Planning）」與「線上執行（Online Execution）」的雙軌分離設計，打造兼具全域預測與即時模擬的數位孿生（Digital Twin）架構：

離線規劃（大腦）： 每次切換模式後，離線驗證線的 OpenDSS 會一次性讀入一整天的排程預測資料。後端會以批次處理（Batch Processing）的方式，快速計算出全天的最優電池排程與總電價，作為基準與驗證標準。

線上執行（現實）： 網頁端即時展示的 01~06 頁面，則是讀取常駐於伺服器記憶體中的 OpenDSS 實體電路。前端會透過定時輪詢（Polling，例如每 N 秒發送一次 API 請求），模擬真實世界中微電網隨時間推進的即時運作行為，該電路會隨著前端的請求逐步推移時間，做到真正的即時狀態更新。

情境範例： 當使用者切換到新模式時，系統的「大腦」已經在背景用 5 秒鐘算完了未來 24 小時的電價結果與最佳排程；而系統的「現實」則將時鐘撥回 00:00，隨著網頁每隔幾秒發出請求，才慢慢推進到 00:15、00:30，就像真實世界一樣。

二、 16 種電路情境定義與優化目標
系統共包含 16 種情境，分為「經過 PSO 優化」與「未經過 PSO 優化」兩大類。
    1.兩段式電價的pso電路
    2.三段式電價的pso電路
    3.兩段式電價包含停電的pso電路
    4.三段式電價包含停電的pso電路
    5.兩段式電價增加負載控制的pso電路
    6.三段式電價增加負載控制的pso電路
    7.兩段式電價包含停電與增加負載控制的pso電路
    8.三段式電價包含停電與增加負載控制的pso電路
和
    1.兩段式電價的不優化電路
    2.三段式電價的不優化電路
    3.兩段式電價包含停電的不優化電路
    4.三段式電價包含停電的不優化電路
    5.兩段式電價增加負載控制的不優化電路
    6.三段式電價增加負載控制的不優化電路
    7.兩段式電價包含停電與增加負載控制的不優化電路
    8.三段式電價包含停電與增加負載控制的不優化電路

PSO 優化核心邏輯：無論是兩段式或三段式電價，PSO 的目標函數皆為「最小化總電費」。演算法會自動尋找在離峰時段充電、尖峰時段放電的最佳策略，同時兼顧停電期間的備用電量與負載控制需求。
    
對照組運作機制：未優化的 8 種電路不放上網站即時運行，後端僅在模式切換時，於背景執行一次完整的 24 小時模擬，取得總電價後，將數據傳遞給主頁做「優化前後電價對比（例如：省了多少錢、尖峰用電減少多少百分比）」。

三、 網站頁面與資料視覺化呈現
系統包含以下頁面，每個頁面都有特定的資料綁定與呈現方式：

主頁（總覽與成效）：
1.狀態標籤：  作為系統預設入口（首次進站預設為「兩段式電價的 PSO 模式」）。主頁僅作「狀態顯示」與「數據呈現」，不包含模式切換功能。清晰顯示當前運作模式（如：三段式電價 + 停電保護 + 負載控制）。
2.圖表展示： 包含 PSO 收斂曲線圖（Line Chart） 展示演算法效能，以及 電池充放電與電網購電狀態的 24 小時預測曲線圖。
3.成效數據（KPI 儀表板）： 動態顯示優化前 vs 優化後的總電價對比與節省金額。
4.01~06 即時狀態頁面： 透過 /api/grid_status 向 server.py 發請求，獲取 JSON 格式的即時數據，並將負載功率、電池 SOC（剩餘電量百分比）、PV 發電量等數值，轉化為儀表板指針、動態長條圖或設備亮燈狀態（On/Off）做即時視覺化。

5.設備控制與停電控制頁面（控制中樞）： 本頁面是全系統唯一的「模式切換」與「參數設定」入口。

6.01~06 即時狀態頁面： 透過 /api/grid_status 向 server.py 獲取 JSON 格式的即時數據，轉化為儀表板指針、動態長條圖或設備亮燈狀態做即時視覺化。

💡 情境範例：一進到「主頁」，能看到主頁的字寫著「當前模式：兩段式電價 PSO」，下方顯示「相比未優化節省了 150 元」。接著點擊「03 3F設備即時狀態」頁面，畫面上會顯示當下虛擬時間（例如 14:30）冷氣正消耗 2kW 的電力冰繪製負載曲線，指示燈顯示為「綠色（開啟）」。

體驗： 畫面上清楚標示「兩段式」與「三段式」，點擊其中一個，另一個就會反灰。直覺且不會出錯。
在「設備控制與停電控制頁面」中，電價方案為必選項，停電與負載控制為可選疊加項：
，介面設計採用「標籤式按鈕（Toggle Buttons）」
點擊停電按鈕開啟向下展開時間輸入框（Time Picker）。
最後用「用 0 跟 1 的陣列去做相乘」這個邏輯，在資料工程與時間序列分析中叫做 「遮罩矩陣相乘 (Masking Matrix Multiplication)」
Step 1: 前端發送 JSON 參數給後端
前端收集完使用者的 UI 選擇後，打包成輕量級的 JSON 發給 server.py。
這樣做的好處：前端不需要處理繁重的陣列運算與檔案生成，且 JSON 格式在網路傳輸上最穩定。
Step 2: 後端 (server.py) 執行「0與1矩陣相乘」生成 CSV
後端收到 JSON 後，利用 Python 的 pandas 或 numpy 套件，來實現你說的完美邏輯。

讀取基礎負載（Base Profile）： 讀取一份寫滿該設備 24 小時功率變化的原始檔案（例如冷氣一整天如果都開著，各個時間點的耗電量）。

生成 0/1 遮罩陣列（Mask Array）： 根據 JSON 傳來的時間，產生一個長度為 96（如果每15分鐘一筆）或 24（每小時一筆）的陣列。在 14:00~16:00 填入 1，其他時間填入 0。


前端防呆與交集檢測： 系統在進行計算前會比對「停電區間」與「設備強制開啟區間」。若重度耗能設備開啟時間與停電時間重疊，前端在發送 API 請求前即予以攔截，彈出警告視窗：「⚠️ 設定衝突警告：停電期間開啟高耗能設備可能導致系統過載無法排程。建議修改時間。」，又或是在電路設定中，斷電後無法開啟的設備會無法選定該時段

檔案生成與狀態重置： 確認送出後，前端將設定參數（JSON）發送給後端。後端將參數寫入負載資料 CSV 檔，並執行嚴謹重置流程：

強制將 OpenDSS 虛擬時間推回 00:00。

清空快取（Cache），並將電池 SOC 重置為初始預設值。

將新負載資料 CSV 與 PSO 算出的排程重新載入記憶體電路中。

閉環驗證流程： 確定模式 ➔ 計算 PSO ➔ 放入離線驗證線做一整天計算：

無過載 ➔ 取得驗證數據 ➔ 回到主頁更新圖表。

有過載 ➔ 產生包含具體過載節點與時間點的警告檔案 ➔ PSO 讀取警告並修正邊界條件重新計算 ➔ 再次驗證直到成功。

五、 等待畫面（State Machine）與例外防護
在 PSO 演算法與離線驗證計算期間，前端實作 5 種狀態的等待遮罩（Overlay Loading Screen），確保良好的使用者體驗：

1.正常路徑： 畫面變暗，顯示「切換模式中...」。
2.觸發過載： 接收到 HTTP 202 狀態碼，畫面文字變更為「遇到電路過載，重新計算排程中...」（觸發閉環修正，最多重試 3 次）。
3.計算完成： 接收 HTTP 200，顯示「切換成功！」，畫面變亮並刷新主頁數據。
4.計算失敗： 若重試 3 次仍過載，顯示「目前設定下找不到不過載的排程方案」。系統將自動觸發回滾機制（Rollback），恢復至上一次成功運行的模式。
5.系統逾時/崩潰： 若 60 秒 Timeout 則顯示「系統回應逾時」；若後端回傳 API 500 則顯示「系統發生錯誤」。

六、 未優化電路之突發停電物理容錯機制
針對 8 種未優化電路，當遇到突發停電（電網斷開）時，若太陽能持續發電但負載極低，極易引發電壓飆升（Overvoltage）導致 OpenDSS 模擬崩潰。本系統於電路模型中內建硬體級別的保護機制：

洩壓電阻（Dump Load）： 將多餘無法消化的電力轉化為熱能消耗。

太陽能降載（Curtailment）： 偵測到異常時，主動降低 PV 的最大功率追蹤（MPPT）輸出。

💡 情境範例： 在「未優化 + 下午1點停電」的情境中，下午 1 點太陽能發電極強（如 10kW）。因為停電，家裡設備斷電只消耗 1kW，而電池剛好滿電。這多出的 9kW 傳統上會讓電壓飆升導致模擬報錯中斷。但系統內建的「洩壓電阻」此時會自動啟動，把這 9kW 以熱能形式消耗掉，確保 OpenDSS 可以安穩地把這 24 小時算完，得出對比基準電價。

七、 程式軟體運行架構與模組分層
系統採用高度模組化的分層架構（Decoupling），確保運作穩定性與開發擴充性：

前端展示與互動層 (Frontend UI Layer)： 負責表單防呆、畫面渲染，利用定時輪詢（Polling）呼叫 API 取得即時數據。

後端中樞控制層 (Backend Server - server.py)： 接收前端 JSON 指令，生成負載 CSV，管控 HTTP 狀態碼，協調底層演算法。

優化演算法層 (Algorithm Engine - PSO)： 獨立 Python 運算模組。讀取負載參數進行決策，輸出排程控制檔；具備讀取「過載警告日誌」並自我修正重算的能力。

雙軌模擬核心層 (Simulation Core - OpenDSS)：

離線驗證器 (Offline Worker)： 背景獨立腳本，批次算完 24 小時潮流，提供基準數據與過載驗證。

線上常駐實例 (Online Memory Instance)： 存活於 server.py 進程記憶體中，每次 API 呼叫僅推進單一 Time Step 進行即時求解。

💡 情境範例： 使用者在前端點擊確認後，前端送出 {"pricing": "two_tier", "outage": ["13:00", "15:00"]} 的 JSON 給 server.py。後端寫出一份負載 CSV；PSO 讀取該 CSV 算出最佳策略並吐出排程 CSV。離線 OpenDSS 拿著兩份 CSV 跑完 24 小時確認沒過載後，前端開始每 3 秒發送一次 GET /api/grid_status，從常駐記憶體的 OpenDSS 拿取如 {"Time": "14:30", "SOC": 65%} 的最新 JSON 數據更新網頁圖表。


八、 檔案生成與讀取生命週期（File I/O Lifecycle）
為防止多模組間的非同步存取錯誤（Race Condition），系統中核心實體檔案的生命週期嚴格遵循以下 5 個時序階段：

階段一 (前端確認 ➔ 產生 Load.csv)： 後端接收到前端變更模式 API 請求的第一時間，覆寫或生成一份全新的負載資料檔。

階段二 (PSO 讀取與計算 ➔ 產生 Schedule.csv)： server.py 主動呼叫 PSO。PSO 啟動瞬間讀取 Load.csv 與電價費率，計算後生成全新的電池排程檔。

階段三 (離線大腦驗證 ➔ 產生數據 或 Warning.log)： 離線驗證線 (Worker) 同時讀取上述兩份 CSV 執行全天模擬。若成功則生成全天數據；若過載則生成紀錄錯誤節點的 Warning.log。

階段四 (閉環修正機制)： 若產生 Warning.log，server.py 將攔截此訊號，要求 PSO 讀取日誌、修正邊界條件並重新生成第二版 Schedule.csv（退回階段三，最多 3 次）。

階段五 (線上現實重置 ➔ 讀取進入即時運行)： 離線驗證確定成功，在回傳 HTTP 200 給前端的前一刻，後端將「記憶體即時電路」推回 00:00，並讓其讀取最終過關的 Load.csv 與 Schedule.csv。此後即時頁面完全依靠這兩份檔案逐秒推演。

💡 情境範例： 使用者設定了「兩段式電價 + 下午 2 點開冷氣」。按下確認的第 1 秒，server.py 瞬間生出 Load.csv。第 2 秒，PSO 立刻抓走檔案並算出 Schedule.csv。第 5 秒，背景離線 OpenDSS 一口氣吃進這兩份 CSV 跑完 24 小時，發現沒有跳電。於是，在第 6 秒，系統把準備給網頁展示的即時 OpenDSS 歸零，並把這兩份過關的 CSV 餵給它。第 7 秒網頁變亮顯示「切換成功」，此時使用者點進即時狀態頁面，看到的已經是這兩份新檔案正在逐秒運作的結果。

    也就是讓使用者在設備控制與停電控制頁面，挑選兩段式電價或是三段式電價，如果只按兩段式電價的按鈕並按下確認，那就是使用兩段式電價pso有再多按設備控制和停電控制按鈕並設定時間，才會是兩段式電價增加負載控制的pso電路或是兩段式電價包含停電與增加負載控制的pso電路，而主頁就單純顯示目前是什麼模式就好

    1.主頁會顯示當前是哪一個模式，一開始在server.py預設使用者第一次進站是兩段式電價的pso，可透過進入設備控制與停電控制頁面切換模式，每次切換模式都會回到00:00重新跑一次，同時在主頁上顯示當前模式server.py也會依照模式去抓取對應模式所需要的資料，同時也抓取對應模式的未優化結果

    設備控制與停電控制頁面要做的事情
    1.使用者透過即時按按鈕觸發停電，要求使用者輸入幾點到幾點停電，按下確定後此時整個系統回到00:00，並套用停電設定重新計算並做顯示，在「設備控制與停電控制」頁面中，為避免使用者輸入在物理上無法執行的極端條件（例如在停電期間強制啟動重型負載，導致系統必定過載），系統會針對使用者設定的「停電區間」與「設備強制開啟區間」進行比對，當偵測到重度耗能設備的開啟時間與停電時間重疊時，在使用者按下「確認」時會優先彈出警告視窗（Modal）：「⚠️ 設定衝突警告： 停電期間開啟高耗能設備可能導致系統過載無法排程。建議修改時間。」

    2.會出現設備，停電，兩段式電價，三段式電價的按鈕，有點像標籤(電價方案為必選項，停電與負載控制為可選的疊加項，兩者互不影響、可同時或分別開啟)
    當按下兩段式電價，點擊設備輸入開關時間，點擊停電輸入開始與結束時間，並產生csv檔案，每當切換模式後會同時向PSO系統還有離線驗證線的opendss提供資料 讓PSO能算出電池充放電策略，讓離線驗證線的opendss算出一整天的理論值，最後才回到網站上面做即時的顯示，會這樣做的原因主要在於要展示PSO算出電池充放電策略的過程數據，以及比對未經優化的總電價(補充說明:流程是 確定好模式>計算PSO並得到電池充放電排程>放入離線驗證線的opendss做一整天的計算並得到優化過後的opendss計算資料(用於驗證)與未優化的opendss計算資料(用於比對)>回到網站做該模式的即時資料顯示以及呈現PSO的計算過程內容與最後的總電價對比)，當使用者在前端確認切換新的電價模式或負載控制時，為了確保活在伺服器記憶體中的「即時 OpenDSS 電路」能正確套用新排程，後端會執行嚴謹的狀態重置流程(強制將 OpenDSS 虛擬時間推回 00:00>清除上一輪的暫存狀態，包含將電池的 SOC（剩餘電量）重置回初始設定值>將新產生的負載資料與 PSO 算出的電池控制排程檔重新載入電路中。)

    3.當使用者在設備控制與停電控制頁面做完這設定並按下確認的時候，在PSO系統跟離線驗證線的opendss計算時，會出現等待畫面，會將畫面變暗，並顯示「切換模式中」的字樣，如過遇到過載情形就顯示 「遇到電路過載重新計算中」字樣 模擬完成後 顯示「切換成功」的字樣，畫面變亮回到主頁

    如果中途一直遇到失敗 例如PSO重新計算好幾次，還是一直過載最多就重試 3 次，3次都失敗的話，改成：停止重試迴圈，回傳「目前設定下找不到不過載的排程方案」的錯誤訊息，附上「哪裡過載」的具體資訊
    其他未知的錯誤涵蓋「非預期錯誤」跟「等太久」的狀況，系統逾時：設一個等待上限（例如 30
    60 秒），如果超過這個時間後端還沒回應（可能是伺服器掛了、卡住了），前端主動跳出「系統回應逾時，請稍後再試」，並提供「重新整理」按鈕

    如果是後端錯誤（例如 API 回傳 500、連線中斷）：跟「過載重新計算中」分開處理，因為過載是「系統正常運作中的一種已知狀況」，使用者知道再等一下就好；但後端崩潰是「系統本身壞了」，這時應該顯示不同的文字（例如「系統發生錯誤，請聯繫開發人員」），避免使用者誤以為只是在正常計算、一直傻等不過

    這樣一來，等待畫面總共會有 5 種狀態：切換模式中 → （過載重新計算中，可能重複最多 3 次）→ 切換成功 這條正常路徑，外加逾時跟系統錯誤 這兩條例外路徑。

補充:本系統包含 8 種「未經 PSO 優化」的對照組電路（情境 1~8），用於計算對比用的基礎總電價。針對未優化電路遭遇「突發停電」時極易發生的系統過載報錯問題，電路模型內建了以下物理級別的容錯處理：
洩壓電阻（Dump Load）： 吸收電網中因突發狀況無法消化的多餘電力。
太陽能降載（Curtailment）： 在電池充滿且無法饋網時，主動降低 PV 輸出。
透過上述硬體級別的模擬設定，確保了即使在未經優化、無智慧排程的惡劣停電情境下，OpenDSS 離線計算依然能完整跑完 24 小時並產出基準電價數據，系統不會因此崩潰。

    其餘01~06的頁面就是透過API向server.py發請求並根據時間抓對應的檔案內的數值(負載消耗功率，電路狀況，PSO的充放電指示、PV發電量)做一個opendss的即時求解得到的數值，server.py 啟動後，build_circuit()（電路建置）和 startup_event() 只在伺服器啟動時執行一次（以及特定情況下才會重新觸發，見下方),不是每次 /api/grid_status 被呼叫就重跑一次。整個 OpenDSS 電路（包含電池物件、SOC 狀態）活在伺服器這個 Python process 的記憶體裡，持續存在，直到伺服器被關掉或重啟
